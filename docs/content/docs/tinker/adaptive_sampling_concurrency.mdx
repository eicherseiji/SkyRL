<Callout type="warn">
These contracts and the queue-delay policy are review scaffolding. No SkyRL training loop or Tinker endpoint composes a
policy yet, and the richer engine-load policy and trajectory-shedding path described below remain proposed.
</Callout>

RL clients know how many logical trajectories they want, but generally do not know the physical capacity of the
inference backend. A fixed client-side trajectory count therefore mixes two concerns:

- **Logical concurrency**: how many trajectories the algorithm may have in progress, including trajectories waiting on
  tools, environments, or inference.
- **Physical sampling concurrency**: how many admission units the inference service should run at once.

Adaptive admission belongs in the component that already owns pending work. In fully async native training that is
`_AsyncStalenessManager`; for Tinker it is `TinkerEngine`. The owner composes one stateful `ConcurrencyPolicy` for each
independently saturated capacity domain. No standalone controller or admission-adapter layer is required.

```text
backend pressure ── SamplingFeedback ──┐
                                      │
completed unit ── SamplingCompletion ─┼─▶ ConcurrencyPolicy ─▶ ConcurrencyDecision
                                      │                           │
owner state ── ConcurrencyContext ────┘                           ▼
                                                     existing admission owner
```

The policy requests effects but never owns queues, durable rows, permits, or tasks. The admission owner applies
`desired_limit` and, when supported, asks its trajectory registry to apply `shed_count`.

## Policy inputs

### `SamplingFeedback`

`SamplingFeedback.metrics` is an extensible `Mapping[str, JsonValue]`. Common keys have stable semantics and units,
missing keys are expected, and specialized backends can add namespaced metrics.

| Common key | Meaning | Typical policy use |
| --- | --- | --- |
| `queue_duration_s` | Time spent queued before generation | Queue-delay AIMD |
| `rate_limited` | Explicit backend capacity rejection | Multiplicative decrease |
| `prompt_tokens` | Prompt work for the completed request | Accounting and future workload-aware policies |
| `completion_tokens` | Realized decode work | Accounting and completion context |
| `cache_hit_tokens` | Prompt tokens served from cache | Cache-efficiency observation |
| `request_latency_s` | End-to-end request latency | Observability; not by itself a capacity signal |
| `engine.loads` | Coherent list of per-engine load objects from one poll | Engine-load-aware admission |

Each `engine.loads` entry has this standard shape:

```python
{
    "engine_id": "decode-0",
    "role": "decode",
    "kv_capacity_tokens": 131_072,
    "max_model_len": 32_768,
    "kv_usage": 0.72,
    "running": 12,
    "waiting": 2,
    "waiting_capacity": 1,
    "preemptions_delta": 0,
}
```

The entire list represents one polling round. This lets an engine-load policy distinguish prefill and decode roles,
aggregate KV capacity, classify queue pressure, and react to preemptions without coupling the policy to a metrics client.
Backends that cannot provide the complete shape omit `engine.loads` and select a less informed policy.

### `SamplingCompletion`

`SamplingCompletion` reports one completed admission unit with its token count, duration, and optional extensible
metadata. In fully async RL the unit is normally a trajectory group, not every model call within a multi-turn trajectory.

The explicit completion hook allows a richer policy to pace growth by pipeline turnover. A metrics poll can declare that
growth is safe, while subsequent completions advance the growth clock. Error completions with zero tokens can be ignored
without mistaking a fast-failing workload for available inference capacity.

### `ConcurrencyContext`

The admission owner captures this context every time it calls a policy hook:

```python
ConcurrencyContext(
    current_limit=32,
    in_flight=30,
    observed_at_s=time.monotonic(),
)
```

`current_limit` and `in_flight` let the policy determine whether admission is binding, compute a new target from current
load, and calculate how much active work must be shed. `observed_at_s` lets a policy expire stale growth permission without
owning a timer or clock.

## Policy output

Both policy hooks return either no action or a `ConcurrencyDecision`:

```python
ConcurrencyDecision(
    desired_limit=24,
    shed_count=6,
    reason="kv headroom hard trim",
)
```

- `desired_limit` controls future admission.
- `shed_count=0` performs a soft trim: the owner blocks new admission and lets current work drain naturally.
- A positive `shed_count` requests active cancellation when that execution path supports it.
- `reason` is suitable for logs and metrics.

The decision deliberately identifies how much work to shed, not which work. In fully async training a separate
`TrajectoryCancellationPolicy` can select the youngest, stalest, least-progressed, or otherwise cheapest trajectories.
Hosted transports that cannot cancel in-flight requests apply only the new admission limit.

## Policies

`ConcurrencyPolicy` has two synchronous hooks so a single owner can serialize state transitions without awaiting inside
the policy:

```python
class ConcurrencyPolicy(Protocol):
    def on_feedback(
        self,
        feedback: SamplingFeedback,
        context: ConcurrencyContext,
    ) -> ConcurrencyDecision | None: ...

    def on_completion(
        self,
        completion: SamplingCompletion,
        context: ConcurrencyContext,
    ) -> ConcurrencyDecision | None: ...
```

The intended policy tiers are:

| Policy | Required visibility | Status |
| --- | --- | --- |
| `EngineLoadConcurrencyPolicy` | Per-engine KV, capacity, queue, role, and preemption data | Proposed |
| `QueueDelayConcurrencyPolicy` | Queue duration or explicit rate limiting | Implemented as a primitive |
| `FixedConcurrencyPolicy` | No trustworthy pressure signal | Implemented fallback |

`QueueDelayConcurrencyPolicy` uses additive increase/multiplicative decrease over feedback intervals. It deliberately
does not infer capacity from token counts or end-to-end latency. A 1-GPU backend and a 16-GPU backend can receive the same
average token load while having very different spare capacity.

```python
import time

from skyrl.utils.adaptive_concurrency import (
    ConcurrencyContext,
    QueueDelayConcurrencyPolicy,
    ResizableConcurrencyLimiter,
    SamplingFeedback,
)

limiter = ResizableConcurrencyLimiter(16)
policy = QueueDelayConcurrencyPolicy(
    max_limit=256,
    queue_duration_target_s=0.2,
)

# The existing admission owner captures its state and applies the decision.
decision = policy.on_feedback(
    SamplingFeedback(
        {
            "queue_duration_s": response.prefill_queue_duration,
            "prompt_tokens": len(prompt_tokens),
            "completion_tokens": len(response.tokens),
        }
    ),
    ConcurrencyContext(
        current_limit=limiter.limit,
        in_flight=limiter.in_flight,
        observed_at_s=time.monotonic(),
    ),
)
if decision is not None:
    await limiter.resize(decision.desired_limit)
```

## Backend mappings

### Native SkyRL / managed vLLM

`VLLMMetricsScraper` already exposes several aggregate load signals. Extending its output with a coherent `engine.loads`
snapshot would make a rich engine-load policy possible. `_AsyncStalenessManager` would compose that policy, enforce the
result together with the algorithmic staleness bound, and provide current admission context.

Selective shedding additionally requires cancellable per-group child tasks and an in-flight trajectory registry. The
long-lived generator worker loop itself must not be cancelled because that would permanently shrink the worker pool.

### Fireworks

Fireworks' Tinker-compatible `DeploymentSampler` reports `prefill_queue_duration`, which maps to `queue_duration_s` and
can drive `QueueDelayConcurrencyPolicy`.

### Tinker

`asample()` should persist the request and return its `APIFuture` without waiting for an admission slot. `TinkerEngine`
would admit durable `PENDING` work in the background and atomically move admitted rows to `DISPATCHED` before launching
engine execution or concurrent forwarding.

A standard Tinker response can provide token and cache summaries but may not expose queue or engine pressure. In that
case `FixedConcurrencyPolicy` is the safe default. Lowering admission can always delay future dispatch; cancelling a
hosted in-flight request requires explicit transport support.

## Engine-load policy compatibility

The contract is intentionally sufficient for a Prime-RL-style controller:

- `engine.loads` carries the coherent capacity and pressure snapshot.
- `on_completion` supports turnover-paced multiplicative growth.
- `ConcurrencyContext` replaces callbacks that read the dispatcher's current limit and in-flight count.
- `desired_limit` expresses growth, soft trimming, and hard cuts.
- `shed_count` expresses the in-flight excess to cancel after a hard cut.

Thresholds, cooldowns, persistence counters, drain mode, escalation state, and initial-limit bootstrap all remain private
state inside `EngineLoadConcurrencyPolicy`. Porting that algorithm does not require another controller abstraction.
